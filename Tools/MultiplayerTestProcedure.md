# NICO DRAW マルチプレイテスト手順

この文書は、Geminiなどの作業エージェントまたは開発者が、NICO DRAWのマルチプレイ回帰テストを再現可能な形で実施するための手順書です。

## 1. 基本方針

- テストは毎回のビルドでは実施しない。
- 変更箇所に応じたテストだけを実施する。
- Directテストはロジック、所有権、同期結果を短時間で確認する用途とする。
- EOSテストは認証、ロビー、P2P通信、再接続を確認する用途とする。
- Unity Consoleに例外がないだけでは合格にしない。位置、速度、所有者、状態遷移、見た目を確認する。
- 同一PCのEOS Device IDで起動した複数プロセスは、同じProductUserIdになる場合がある。実EOSの4人試験は原則として4つの独立した認証環境で行う。

## 2. テストを実行するタイミング

### 通常の小変更

ローカライズ、背景画像、単純なUI配置など、通信やゲーム進行へ影響しない変更ではマルチプレイテストは不要。

Unityのスクリプトコンパイルエラーが0件であることだけ確認する。

### 関連機能を変更したとき

次のいずれかを変更した場合は、該当するDirect自動テストを実施する。

- `OnlineManager`、オンラインバックエンド、プレイヤー同期
- プレイヤー生成、番号、色、アバター、途中参加
- DRAW確定、BodyData、インク上限
- 持ち上げ、投げ、接地、死亡、リスポーン
- 鍵、ボタン、爆弾、球、木箱などの同期ギミック
- 小部屋、チャレンジ開始、ゲームオーバー

### リリース候補

リリース候補では次を実施する。

1. Directの主要自動テスト一式
2. 4つの独立認証環境を使った実EOS試験
3. 2時間以上のソークテスト
4. 今回修正した機能の手動重点確認

## 2.1 回帰テストと新規不具合探索を分ける

この文書のコマンド指定テストは、主に既知不具合の再発を検出する回帰テストである。回帰テストがすべてPASSでも、新しい種類の不具合がないことは保証できない。

テスト実施時は、次の2種類を別々に実施、報告する。

### 回帰テスト

- 過去に発生した不具合が再発していないか確認する。
- 手順、入力、期待結果が決まっている。
- 自動テストのPASS/FAILで判定する。

### 新規不具合探索

- 既知の期待結果だけをなぞらず、不自然な状態やクライアント間差異を探す。
- 操作順、担当プレイヤー、ステージ、描画形状を毎回変える。
- 発見がなくても、実施した範囲と未確認範囲を報告する。
- リリース候補では総テスト時間の20%以上を探索テストへ割り当てる。

## 2.2 新規不具合を検知する共通不変条件

既知の不具合名ではなく、ゲーム中に常に成立すべき条件を監視する。次のいずれかが崩れたら、新規不具合候補として記録する。

### プレイヤーと所有権

- ロビー人数とステージ上の有効プレイヤー数が一致する。
- 有効なPlayer IDは全員異なる。
- 1つのPlayer IDに複数のアバターが割り当てられない。
- 1つのアバターを複数クライアントがローカル所有しない。
- ローカル入力で動くのは所有プレイヤーだけである。
- 番号、色、名前、種族の対応が全クライアントで一致する。

### Transformと物理

- 座標、速度、回転にNaNまたはInfinityがない。
- 通常移動で説明できない大きな瞬間移動がない。
- 動くべき物体の更新時刻が一定時間以上止まらない。
- 静止すべき物体がクライアントごとに異なる方向へ移動しない。
- 持ち上げ、投げ、死亡の後にRigidbodyとColliderが有効へ戻る。
- 接地可能な床上でGroundedが長時間falseのままにならない。

### 状態遷移

- DRAW、死亡、復活、持ち上げ、操作可能、ステージクリアが矛盾した組み合わせにならない。
- リスポーンは一定時間内に完了する。
- 同じプレイヤーが短時間に無限リスポーンしない。
- カウントダウン、プレイ中、クリア、ゲームオーバーが逆戻りまたは多重開始しない。
- ホスト確定済みのギミック状態が一定時間内に全参加側へ到達する。
- 途中参加者へ現在状態が復元され、初期状態へ巻き戻さない。

### UIとオーディオ

- ゲーム中に理由なくDRAW、タイトル、ステージ選択画面へ移動しない。
- 操作不能のUIが画面を塞いだまま残らない。
- 同じ効果音が短時間に異常な回数再生されない。
- 画面外に必要情報、プレイヤー、復活地点が固定されない。

現在の自動テストは、ID重複、人数、位置差、種族差、NaN/Infinity、一部の復活・球移動・状態遷移を検査している。それ以外は手動観察またはテレメトリ解析が必要であり、自動検査済みとして報告してはならない。

## 2.3 探索テストの選び方

毎回同じ操作をしない。テスト開始前に、次から最低3項目を選び、選択内容を報告へ残す。

- ホストと参加側の役割を入れ替える。
- P2、P3、P4の別々の参加側からギミックを操作する。
- 2人以上が同時にDRAW、死亡、持ち上げ、投げを行う。
- DRAW確定中に別プレイヤーが参加または退出する。
- 持ち上げ中に運搬者または対象者が死亡する。
- カウントダウン中に退出、再参加する。
- ステージクリア直前またはゲームオーバー直前に退出する。
- 最大幅、最大高さ、極端に細い、左右非対称な身体を使用する。
- 同じギミックを複数人が同時に操作する。
- 同じステージをリトライせず連続遷移する場合と、何度もリトライする場合を比較する。
- 日本語と英語のクライアントを混在させる。
- 低フレームレートまたはバックグラウンド状態のクライアントを混ぜる。

操作の組み合わせは固定せず、前回と同じ組み合わせだけにならないようにする。

## 2.4 推奨実行周期

毎ビルドではなく、次の周期を目安にする。

| タイミング | 実施内容 |
| --- | --- |
| 通常開発 | 変更箇所に対応するDirect回帰テストだけ |
| マルチプレイ関連PR完了時 | 関連回帰テストと15分以上の探索テスト |
| 夜間または週数回 | ステージと操作順を変えたDirect 4人テスト |
| 週1回または大型変更後 | 4環境で実EOS、途中参加、再接続 |
| リリース候補 | 全回帰、実EOS、2時間ソーク、探索テスト |

夜間テストを自動化する場合は、実行シード、ステージ、操作順を保存する。同じシードで再現できないランダムテストは不具合調査に使いにくいため、シード未記録の完全ランダム操作は禁止する。

## 3. 事前確認

PowerShellをプロジェクトルートで開く。

```powershell
Set-Location C:\workSpace\PICO
```

作業中の変更を確認する。

```powershell
git status --short
```

既存の未コミット変更を削除、復元、上書きしないこと。

Unityのバージョンは`6000.1.2f1`を使用する。テスト中は同じプロジェクトをUnity Editorで開かない。

## 4. テストビルド

### Unityメニューから作る場合

Unityで次を実行する。

```text
PICO > Build Windows Demo Multiplayer Test
```

出力先:

```text
Builds/NICO DRAW Demo Test/NICO DRAW.exe
```

### コマンドラインから作る場合

```powershell
& 'C:\Program Files\Unity\Hub\Editor\6000.1.2f1\Editor\Unity.exe' `
  -batchmode -nographics -quit `
  -projectPath 'C:\workSpace\PICO' `
  -executeMethod DrawBody.EditorTools.WindowsBuildMenu.BuildWindowsDemoMultiplayerTest `
  -logFile 'C:\workSpace\PICO\Temp\demo-multiplayer-build.log'
```

終了コードだけで成功判定しない。必ずログを確認する。

```powershell
Select-String Temp\demo-multiplayer-build.log `
  -Pattern 'error CS|Build failed|Windows demo multiplayer test build created'
```

合格条件:

- `error CS`が0件
- `Build failed`が0件
- `Windows demo multiplayer test build created`が存在
- EXEと`Assembly-CSharp.dll`の更新日時が今回のビルド時刻になっている

## 5. Direct自動テスト

各コマンドは4つの独立したゲームプロセスを起動する。ポートが重複した場合は、未使用の別ポートへ変更する。

### 5.1 基本同期

```powershell
.\Tools\RunDemoMultiplayerSmokeTest.ps1 `
  -Players 4 -Stage 14-3 -Port 19433
```

確認内容:

- 4人が同じロビーへ入る
- Player IDが欠落、重複しない
- 各プロセスが自分のプレイヤーだけを操作する
- DRAW確定後の身体が全クライアントへ届く
- 座標差、種族差、Unity例外が許容範囲内

### 5.2 同時DRAW

```powershell
.\Tools\RunDemoMultiplayerSmokeTest.ps1 `
  -Players 4 -Stage 14-3 -ConcurrentRedraw -Port 19434
```

確認内容:

- 複数人が同時にDRAWを確定しても身体が入れ替わらない
- 他人の見た目がローカルプレイヤーへ上書きされない
- DRAW終了後に操作が戻る

### 5.3 途中参加

```powershell
.\Tools\RunDemoMultiplayerSmokeTest.ps1 `
  -Players 4 -Stage 1-1 -LateJoin -SkipRedraw -Port 19435
```

確認内容:

- 3人で開始した後に4人目が参加できる
- 既存プレイヤーのID、番号、見た目が変わらない
- 途中参加者に4体と現在のステージ状態が復元される
- 参加後も各プレイヤーが自分だけを操作する

### 5.4 小部屋

```powershell
.\Tools\RunDemoMultiplayerSmokeTest.ps1 `
  -Players 4 -Stage 9-3 -ReadyRoomSmoke -SkipRedraw -Port 19436
```

確認内容:

- 上下どちらの部屋からも上のモニター全体が見える
- 枠外へ落下しても割り当てられた部屋へ復活する
- 復活と落下を無限に繰り返さない
- 後から別プレイヤーが描き直しても準備済みプレイヤーがボタンからずれない
- ボタン上では緑表示が維持される
- 4人準備後に対象ステージが開始する

### 5.5 8-2の球と残機

```powershell
.\Tools\RunDemoMultiplayerSmokeTest.ps1 `
  -Players 4 -Stage 8-2 -SkipRedraw -Port 19437
```

確認内容:

- ホストと参加側の全画面で球が動き続ける
- 2球中1球が落ちた場合は残数だけ1減り、ゲームは継続する
- すべての有効な球が落ちた場合だけ再カウントダウンする
- 残機0でゲームオーバーになる

### 5.6 参加側の猫Fと爆弾

```powershell
.\Tools\RunDemoMultiplayerSmokeTest.ps1 `
  -Players 4 -Stage 2-1 -CatBombSmoke -SkipRedraw -Port 19438
```

確認内容:

- 参加側P2の猫F攻撃が爆弾へ当たる
- ホストが爆発を確定する
- 全クライアントから同じIDの爆弾が消える
- 爆発が重複適用されない

### 5.7 未知バグ探索ソーク

既知の再現手順に依存せず、4人が移動、ジャンプ、F操作をランダムに繰り返す。
同じ`Seed`なら同じ操作系列になるため、異常を再現するときは値を変えない。

短い動作確認:

```powershell
.\Tools\RunDemoMultiplayerSmokeTest.ps1 `
  -Players 4 -Stage 1-1 -SoakSeconds 60 -Seed 1337 -Port 19439
```

通常の探索試験:

```powershell
.\Tools\RunDemoMultiplayerSmokeTest.ps1 `
  -Players 4 -Stage 1-1 -SoakSeconds 1800 -Seed 1337 -Port 19439
```

ステージまたは操作系列を変えて繰り返す場合は、`Stage`、`Seed`、`Port`を変更する。
ビルドのたびには実行せず、オンライン、物理、キャラクター操作を変更した後とリリース候補で実行する。

自動監視する内容:

- Player IDとスロットの重複、途中での割り当て変更
- クライアント間の位置、人数、アバター状態の不一致
- NaN、Infinity、異常速度、不可解なテレポート
- 空中での静止、5秒以上終わらないリスポーン、消失したアバター
- 脱落済みキャラクターに有効な非Trigger Colliderが残っていないこと
- Unity例外とエラー
- テスト終了時に全プレイヤーが観測できること

このモードは未知バグを見つける確率を上げるものであり、ステージ攻略、DRAW、途中参加、実EOSの専用試験を置き換えない。

## 6. 自動テスト結果の判定

成功時はPowerShellへ`Result: PASS`が表示され、終了コードが0になる。

成果物は次へ保存される。

```text
Temp/DemoMultiplayerSmoke/<run-id>/
```

重要なファイル:

- `report.md`: 人が読む要約
- `report.json`: 機械判定用の全結果
- `client-*.json`: 各クライアントの観測結果。番号は起動時の固定クライアント番号
- `client-*-unity.log`: 各Unityプロセスのログ
- `telemetry-client-*.jsonl`: 時系列の位置、速度、状態。番号はゲーム内スロットではなく固定クライアント番号
- `*.png`: 対応シナリオの画面証跡

合格条件:

- 全プレイヤーが`PASS`
- Unity例外が0件
- Player IDの重複が0件
- 座標差が`PositionTolerance`以下
- 通常シナリオでは全クライアントの種族認識が一致
- 同一ロスター内のPlayer IDとスロットが一意
- 同じPlayer IDのスロットが途中で変化しない
- 同じUTC時刻に、全クライアントで`PlayerId -> slot`の対応が一致
- テレメトリ監査が正常に完了し、不変条件違反が0件

テレメトリには`capturedAtUtc`、`processId`、`clientInstance`、`rosterRevision`、`rosterSignature`を記録する。`elapsedSeconds`はプロセスごとに起点が違うため、クライアント間比較には使わない。

監査はPython 3で`Tools/analyze_telemetry_invariants.py`を実行する。Pythonが見つからない、JSONが壊れている、監査スクリプトが異常終了した場合もテストは`FAIL`とする。

単独で監査結果を確認する場合:

```powershell
python .\Tools\analyze_telemetry_invariants.py `
  .\Temp\DemoMultiplayerSmoke\<run-id>
```

失敗した場合、同じテストを無条件に何度も再実行して合格扱いにしない。まず`report.md`、失敗したプレイヤーのJSON、Unityログ、テレメトリの順に原因を調べる。

## 7. 実EOSの4人テスト

### 必要な環境

- 4台のPCまたはVM、あるいは4つの独立したSteam/Epic認証環境
- 全端末で同じビルド
- 各端末で異なるProductUserId
- ホスト1台、参加側3台

同一Windows端末でフォルダーや`TEMP`だけを分離しても、EOSが同じProductUserIdを返す場合がある。この状態の4人テストは無効とする。

### 手順

1. 全端末でゲームを起動する。
2. 各端末のオンライン表示名と認証済みユーザーが異なることを確認する。
3. ホストが非公開ルームを作成する。
4. 参加側3台がルームコードで参加する。
5. 全端末で4人の名前、番号、色、見た目を読み上げて照合する。
6. 全員READYにしてステージ1-1を開始する。
7. 参加側のうち1台をステージ中に終了し、再起動して途中参加する。
8. 再参加後に既存3人の番号と見た目が変化していないことを確認する。
9. 各プレイヤーがDRAWを1回ずつ確定する。
10. 2人が同時にDRAWを確定する。
11. 参加側が別プレイヤーを持ち上げ、左右それぞれへ投げる。
12. 鍵、鍵穴、ボタン、木箱などを参加側が操作する。
13. 1-2で風船の銃の球が全端末で命中しているか確認する。
14. 8-2で球が参加側でも止まらないことを確認する。
15. 9-3の小部屋で落下復活、モニター、ボタン表示を確認する。
16. 猫で爆弾をF攻撃し、全端末で同時に消えることを確認する。

### EOS固有の不合格条件

- `search failed invalid auth`
- 同じProductUserIdが2台以上に現れる
- 参加または再参加で既存プレイヤーの番号が変わる
- ロビーは4人なのにステージ上のプレイヤーが4体でない
- ホストでは動く物体が参加側だけ停止する
- 切断後に古いプレイヤーが残る

## 8. 2時間ソークテスト

リリース候補では4人で最低2時間継続する。

30分ごとに次を繰り返す。

1. 全員が1回DRAWを確定する。
2. 1人が離脱し、再参加する。
3. 各プレイヤーが別のプレイヤーを持ち上げて投げる。
4. 全員が死亡または落下し、復活する。
5. ギミックを参加側から操作する。
6. ステージを変更する。

常時監視する項目:

- 同じプレイヤー番号が複数存在しない
- 自分の見た目が他人の見た目へ変化しない
- 棒立ちのまま更新されないプレイヤーがいない
- 不自然なテレポートがない
- 接地不能、浮遊、操作不能がない
- 同じSEが多重再生され続けない
- リスポーンが連続して止まらない状態にならない
- 球、木箱、鍵などの位置が端末間で一致する

異常が出たら、発生時刻、ステージ、ホストか参加側か、直前の操作を記録する。可能なら全端末の画面録画時刻を合わせる。

## 8.1 全ステージ横断探索

リリース候補では、主要テストで対象にしていないステージも一度は4人で開始する。

各ステージで最低限、次を行う。

1. ホストではなく参加側が最初のギミックを操作する。
2. 1人がDRAWを確定する。
3. 2人が接触、持ち上げ、投げを行う。
4. 1人が死亡または場外落下する。
5. 可能なら1人が途中退出、再参加する。
6. 全クライアントのプレイヤー数、ID、位置、種族、ギミック状態を比較する。

ステージ固有の正解操作を完遂できなくても、不変条件の監視は続ける。未攻略を通信不具合として記録せず、操作不能、状態不一致、停止、例外と区別する。

## 8.2 通信条件を変える探索

利用可能な安全なネットワーク試験環境がある場合、次を個別に試す。

- 100msから300msの遅延
- 1%から5%のパケット欠落
- 一時的な通信停止と復帰
- ホスト以外のバックグラウンド化
- 参加側だけ低フレームレート

一度に複数条件を加えず、条件と適用端末を記録する。OSやネットワーク全体へ影響するツールを無断で導入しない。環境を用意できない場合は未実施と明記する。

重点確認:

- 入力予測後の位置がホスト確定値へ不自然に往復しない。
- 古いsequenceやrevisionが新しい状態を上書きしない。
- 一時停止後にスナップショットで復旧する。
- リクエストの再送でギミックが二重発動しない。
- 切断扱いになったプレイヤーが残留しない。

## 8.3 テレメトリによる未知異常の探索

既知の`failedChecks`だけでなく、JSONL全体を調べる。

確認する変化:

- 位置または速度が突然極端な値になる時刻
- respawningが長時間trueのままの区間
- groundedが床上で長時間falseの区間
- controlsEnabledがDRAW終了後もfalseの区間
- 同じslotのplayerIdが途中で変化する箇所
- 同じplayerIdのspeciesがクライアント間で異なる区間
- 動くギミックの座標が1台だけ更新されない区間
- 短時間に同じ状態を行き来する箇所

しきい値外の値がなくても、ホストと参加側の時系列グラフの形が大きく異なる場合は調査対象にする。

## 9. 今回の不具合別手動チェック

### プレイヤー番号と見た目

1. 4人で参加する。
2. 各自が異なる形へ描き直す。
3. 全端末でP1からP4の見た目を照合する。
4. 1人が途中退出、再参加する。
5. 再度照合する。

### 投げ同期

1. 参加側が人キャラになる。
2. ホストを持ち上げる。
3. 左右と上方向へそれぞれ投げる。
4. ホスト画面と参加側画面で、離す時刻、初速、着地点を比較する。
5. 投げられた後に接地と操作が戻ることを確認する。

### 描画サイズとスタック

1. 太い胴体、長い腕、長い尻尾を上限内で作る。
2. 狭い通路、段差、壁際へ入る。
3. 持ち上げ、投げ、死亡、DRAW確定を順に試す。
4. 永久スタックや接地不能にならないことを確認する。

### オーディオ

1. 4人が短時間に連続死亡する。
2. 同じ効果音が音量加算されて爆音にならないことを確認する。
3. リトライとステージ再読み込み後に古い音が残らないことを確認する。

## 10. 失敗時の調査順序

1. `report.md`で失敗シナリオとプレイヤーを特定する。
2. 対応する`client-*.json`の`failedChecks`と`lastAction`を見る。
3. `client-*-unity.log`で例外、認証、切断、再接続を調べる。
4. `telemetry-client-*.jsonl`で問題発生前後のUTC、`playerId`、`slot`、位置、速度、respawning、speciesを比較する。
5. ホストと参加側で同じobjectId、playerId、sequence、revisionになっているか確認する。
6. Directだけ失敗するか、EOSだけ失敗するかを切り分ける。
7. 再現条件が判明してから修正する。
8. 修正後は失敗したシナリオと、その周辺シナリオだけを再実行する。
